# 充分验证配方

核心原则（`CONSTITUTION.md` 第四条）：**证据高于声明。**
"看起来没问题""应该可以"不是验证，是猜测。任何"完成"，都要附命令与输出。

---

## 一、验收标准必须先能判定

开工前把每条 AC 写成下面两种形式之一：

```
AC1：运行 `npm test -- order` → 期望 0 failed
AC2：运行 `curl -s -o /dev/null -w '%{http_code}' ...` → 期望 201
AC3：人工确认：取消订单后列表页不再出现该订单（截图/录屏）
```

写不出命令的 AC，说明任务还没想清楚 → 改用 recon 模式先调研。

**AC ↔ 命令映射表**在 `TASK.md`「验收标准」里逐条打勾。收尾时逐条复跑，不允许"上次跑过了"。

---

## 二、行为变化必须有红绿证据

改行为（加功能、修 bug、改语义）时的固定动作：

1. **红**：先写一个会失败的测试（或复现脚本），运行，**看到它失败**，把失败输出摘要记进 `TASK.md`「红绿证据」。
   - 没有复现证据就不要改代码 —— 你会不知道自己在修什么。
2. **绿**：写最小实现让它通过，运行，记录通过输出。
3. **重构**：在测试保护下整理代码，测试保持全绿。

反模式（审计与评审会查）：

- 先写实现再补一个"刚好通过"的测试
- 测试断言写得比实现还宽松（`expect(x).toBeDefined()` 这种）
- 为了让测试变绿去改测试、加 `skip`、删用例 —— 这是本套规范里最严重的违规

### 二·补：行为不变类改动（重构 / 改名 / 格式化）的等价性证据

重构没有"红"可看 —— 它本来就不改变行为，先写一个失败测试是装样子。
但"没有红绿"不等于"没有证据"：重构的证据是**等价性**，要逐条机检，别用"应该没改行为"糊过去。

四条等价性证据（能全给就全给，给不了的写明为什么）：

1. **测试通过数不变**：改前改后都跑全量，**通过项数一字不差**（如 194 → 194）。
   数字变了就必须解释是哪一项多/少了，而不是"反正全绿"。
2. **不做任何"顺手"的语义改动**：改动只应是"把一段代码搬到有名字的函数里"。
   `git diff` 逐点看；抽出的函数名要说明它做了什么（`reconnect_with_backoff`、`push_port_gauges`），
   不是 `do_stuff`；也不允许顺手加单行转发包装。
3. **不新增抑制手段**：`git diff` 里新增的 `#[allow(clippy::…)]` / `eslint-disable` / `unwrap()` 计数必须为 0
   （`git diff -U0 | grep -c '^+.*allow\('` 这类命令直接数）。
4. **改前数字要能复测**：卡面里的"改前 / 改后"数字必须由同一条命令、同一口径产生。
   已提交后再补"改前"数字的办法是开一个临时工作树：
   `git worktree add --detach /tmp/before <改前提交>`，在那个工作树里跑同一条命令，跑完 `git worktree remove --force`。

若重构由**并行子代理**分片完成（一个任务卡内、文件互不相交），加两条：

- 主控必须独立复跑全量验证与 `git status`（子代理"我这边通过了"不是证据）；
- **子代理自报的数字一律复测**（实测出现过子代理报 74 行、主控复测 60 行的差异），
  卡面只写主控复测过的数字。

### 二·补二：任何数字都要跟一条命令和一个口径

卡面、`ROADMAP.md`、验收表里的每个数字（违规数、函数长度、性能、覆盖率）都必须紧挨着产生它的命令，
并写清口径。混口径的代价很实在：实测过一个仓库把"`unwrap_used` 约 110 处"（含测试目标）
当成生产目标的数字，据此把任务粒度判断错了，最后不得不拆卡返工；
同一条 lint 在"生产目标"与 `--all-targets` 下是 63 与 312 的差别。

写法对照：

```
差的写法：unwrap_used 违规约 110 处，开了 G-3 收敛
好的写法：`cargo clippy --workspace --message-format=short -- -W clippy::unwrap_used` → 63 条
          （口径：生产目标；加 --all-targets 另有 249 条，不计入本次收敛范围）
```

## 三、分层验证：不同阶段跑不同的量

| 层级 | 什么时候跑 | 内容 | 命令 |
|---|---|---|---|
| 单文件 | 每改完一个文件 | 该文件相关的单元测试 | `npm test -- <pattern>` |
| 一步 | 每完成计划里的一步 | `verify --fast` | `scripts/verify.ps1 -Mode fast` |
| 一个任务 | 任务收尾（必跑） | `verify --full`（含全量测试 + 一致性审计 + 门禁自测） | `scripts/verify.ps1` |
| 一个模块 | 模块收尾（必跑） | `verify --full` + 该模块的端到端路径 | 同上 + 模块 README 的测试命令 |
| 整个项目 | 全部模块 done 后 | `ROADMAP.md` 里程碑验收清单 | 逐项执行并记录 |

**不要每步都跑全量**（慢，且会把注意力从失败点引开）；**也不要收尾不跑全量**（会漏掉跨模块回归）。

---

## 四、测试该覆盖什么

每个新增分支至少覆盖：

1. 正常路径（happy path）
2. 至少一条**失败路径**（输入非法 / 依赖报错 / 超时）
3. 至少一条**边界**（空集合、0、负数、最大值、首尾元素、并发）

另外值得单独测的：

- 幂等性（重复执行同一操作结果不变）
- 排序与分页的稳定性
- 时间与随机源（必须可注入，否则测不了）

不追求覆盖率数字；追求"每个 if 的另一半都有人走过"。

---

## 五、不可自动化部分的验证

有些 AC 只能人工确认（界面观感、性能体感、真实设备行为）。处理方式：

- 在 `TASK.md` 的 AC 里明确标"人工确认"，写明**确认步骤与观察点**（不要只写"确认没问题"）。
- 人工确认也要留痕：截图/录屏路径或一句"由 XXX 在 YYY 环境确认"。
- 不要把"人工确认"当兜底逃逸口 —— 能写成命令的，一律写成命令。

---

## 六、证据留档规则

- 每次 `verify` 自动落盘 `var/verify-<时间戳>.log`；`TASK.md` 只记录**路径 + 结论**，不复制大段输出。
- 红绿证据记在 `TASK.md`「红绿证据」一节，带命令与时间。
- 归档任务卡（`docs/tasks/`）保留这些内容 —— 下一个人靠它判断"这个结论可不可信"。
- `consistency-audit` 会检查：有模块标 `done` 却没有任何 `var/verify-*.log` → 直接失败。

---

## 七、验证失败的处置

1. 自己先看失败输出，不要立刻改代码猜原因。
2. 判断是"实现错"还是"测试错"：**默认是实现错**。断定测试写错必须有理由，并走测试变更申报。
3. 修不了 / 依赖外部条件 → 把任务标 `blocked`，在 `TASK.md` 写清：失败现象、已排除的可能、需要什么。
4. 不允许把失败测试注释掉、加 `skip`、或降低断言来"通过"。

---

## 八、收尾必跑的完整清单

```bash
# Windows
scripts/verify.ps1                 # 全量：范围门禁 + 一致性审计 + 格式 + lint + 类型 + 测试 + 门禁自测
# 其他平台
scripts/verify.sh
```

逐条确认：

- [ ] scope-check 通过（没有越界改动；若打印了"死信"警告，说明白名单写法有问题，先修写法）
- [ ] consistency-audit 0 error（warning 已逐条解释；先看它打印的 `计划源=… 归档=… 证据=…` 是否与实际目录一致）
- [ ] 全量测试通过（不是"只跑了相关测试"）
- [ ] 两个门禁自测通过（scope-check 11 passed / consistency-audit 26 passed；用例数改了要同步这一行）
- [ ] AC 逐条复跑并打勾
- [ ] 红绿证据齐全（行为不变类改动则给等价性证据，见二·补）
- [ ] 卡面里每个数字都跟了命令与口径（见二·补二）
- [ ] 日志路径已写进 `TASK.md`
- [ ] 与规则/脚本本身有关的问题已记入本轮回流（见 `CHANGELOG.md`，收尾时问一句）
