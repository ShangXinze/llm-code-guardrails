# TASK.md 填写要点

`TASK.md` 是整套规范里最容易被改坏的文件。三个常见错误：

## 错误 1：验收标准无法判定

| 差的写法 | 好的写法 |
|---|---|
| 代码整洁、结构清晰 | 新增函数 `parseOrder` 圈复杂度 ≤ 10，`npm run lint` 通过 |
| 功能正常 | 运行 `npm test -- order` 全绿；手工 POST `/orders` 返回 201 且 body 含 `id` |
| 兼容老版本 | 运行 `npm run test:compat`，输出 `0 failed` |

写到写不出命令的程度，就说明这个任务该走 recon 模式先调研。

## 错误 2：白名单写得太宽或太窄

- 太宽（整个 `src/`）→ 门禁形同虚设，LLM 会开始"顺手"。
- 太窄（只给一个文件）→ 任务进行到一半就开始写"范围变更请求"，浪费来回。
- 判据：把「完成这个任务**最少**要动的文件/目录」列出来，再加一个模块目录作为余量。

格式要求（`scope-check.mjs` 直接解析，写错会解析失败）：

```
<!-- SCOPE:MODIFY:BEGIN -->
TASK.md
src/modules/order/
<!-- SCOPE:MODIFY:END -->
```

- 目录以 `/` 结尾，单文件写完整相对路径
- 一行一个，**不要项目符号、不要反引号、不要行内注释**
- `#` 开头的行会被忽略，可作注释
- 允许新建的文件写进 `SCOPE:CREATE`，否则算越界

### DENY 的语义：DENY 优先，写错就是死信

判定顺序是 **DENY → CREATE/MODIFY**（`scope-check.mjs` 里命中 DENY 直接 continue）。
所以 DENY 与 CREATE/MODIFY 有重叠时，**DENY 永远赢**，那些 CREATE/MODIFY 项写进去也永远不会被放行：

```
差的写法（本项目真实踩过）：
SCOPE:CREATE: docs/任务归档/      ← 于是这张卡永远写不进归档卡
SCOPE:DENY:   docs/               ← 整目录 DENY 把它盖住了

好的写法：把 DENY 收窄到具体文件
SCOPE:DENY:   docs/使用手册.md
              docs/协议规范.md
```

- 脚本会在 DENY 目录项覆盖 CREATE/MODIFY 项时打印"死信"警告（判定不变，只提示）。
  看到这条警告就改写法，不要去找绕过办法。
- 只比较非通配项：`crates/*/Cargo.toml` 这类 glob 按字面量匹配，不覆盖 `crates/` 整棵树，不会被误报。
- 目录以 `/` 结尾的写法按"覆盖其整棵子树"处理（这也是 `hit()` 的语义），
  所以 `docs/` 与 `docs/使用手册.md` 不是一回事。

## 错误 3：进度日志事后补写

进度日志的价值在于"当轮的真实判断"，事后补写会美化过程、丢掉踩过的坑。
规矩是：**改完一个文件就追加一行**，格式固定：

```
- 2026-09-16 10:00：完成参数校验。修改：`src/modules/order/service.ts`。验证：`npm test -- order`。下一步：补测试。
- 2026-09-16 10:30：测试失败，标记 blocked。原因：……。需要：……
```

## 轮次记录怎么用

每轮开始时把复述块追加进「轮次记录」（不覆盖旧轮次）。它有两个作用：

1. 证明 Agent 确实走了启动流程，而不是直接开写；
2. 长任务被中断后，新会话能从这里恢复"当时认为的目标/边界是什么"，
   这比从 `git log` 里猜要可靠得多。

第 3 轮以后，如果复述块里的目标已经和最初不一样，说明任务在漂移 —— 停下来确认，而不是继续写。

## 错误 4：数字没有命令与口径

"约 110 处违规""大概 300 行"这类估数是拆任务、定范围的依据，口径混了就必然判断错
（实测：把含测试目标的 110 处当生产目标，任务粒度判断错、被迫拆卡返工；同一条 lint
生产目标 63 处、`--all-targets` 另有 249 处）。规矩：**每个数字紧挨着一条可复制的命令**，
并写明口径；跨轮比较必须同命令同口径。要补"改前"的数字，用临时工作树去旧提交上跑，别凭记忆：

```bash
git worktree add --detach /tmp/before <改前提交>
cd /tmp/before && cargo clippy --workspace --message-format=short -- -W clippy::too_many_lines
```

## 一张卡内可以并行子代理，但有四条约束

"一次只做一张任务卡"约束的是**任务卡**，不是"只能单线程干活"。一个卡内派多个子代理分片改
是允许的（实测 5 个子代理并行重构 13 处，效率明显更高），但：

1. **文件不相交**：每个子代理负责的文件集互不重叠，白名单仍由主控单点定义；
2. **只做计划里的那件事**：如抽取式重构就只搬代码，不许顺手改语义、不许加 `#[allow]`；
3. **子代理不要跑格式化**（多人同时 `cargo fmt` / `prettier` 会互相踩），格式化与最终校验留给主控；
4. **子代理的自报不算证据**：`git status`、全量测试、卡面里的数字一律由主控复跑复测
   （实测出现过子代理自报 74 行、主控复测 60 行的差异）。

## 流程偏差要如实写进卡面

护栏的可信度来自"偏差被上报"而不是"过程看起来顺利"。漏了复述就开始改代码、越界后又补手续、
探针忘删又删掉 —— 这些都写进 `TASK.md` 的「流程偏差申报」，写清：事实 / 影响 / 缓解 / 后续做法。
不要写成"事后补记"来淡化；下一轮的人（和新会话的自己）要靠这条判断卡面的可信度。
