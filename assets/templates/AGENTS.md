## 1. 目标与非目标

目标：用最小变更完成明确任务；保持可读、直接、线性；不破坏既有架构与契约。
非目标：顺手重构、升级依赖、引入新框架、任务范围外的优化、格式化无关文件。

## 3. 启动流程与门禁

**冷启动**（新会话或新任务）：按序读 `AGENTS.md` → `CONSTITUTION.md` → `ROADMAP.md`（只看当前模块与任务）
→ `TASK.md` → 当前模块 `README.md` → 相关源码与测试 → `scripts/verify.*` 顶部命令配置。

**热续**（同一任务继续）：只读 `TASK.md` + 上一步变更的文件 + 当前模块 `README.md`。
其余按需查阅，不要每轮全量重读（会挤掉真正需要的上下文）。

读完必须把复述块写入 `TASK.md` 的「轮次记录」：

```
目标 / 非目标 / 验收标准 / 允许修改 / 禁止修改 / 风险 / 计划修改文件及理由
```

门禁：`TASK.md` 中 `approval: human` 时必须等人类确认；仅 `auto` 可直接执行。默认 `human`。
**未完成复述，禁止修改任何代码。**

**侦察模式（recon）**：任务尚未明确时，在 `TASK.md` 声明 `mode: recon`。只读源码，只允许写 `docs/notes/`，
产出「现状说明 + 建议方案 + 建议范围」，确认后转 `mode: execute`。不要为了过门禁而编造范围。
## 4. 范围锁（由脚本强制执行）

白名单**单点定义在 `TASK.md`** 的哨兵块（`SCOPE:MODIFY` / `SCOPE:CREATE` / `SCOPE:DENY`），其他文档不得再声明一份。

- 越界：立即停止 → 在 `TASK.md` 写「范围变更请求」（原因 / 文件 / 风险）→ 等待确认。
- 机器校验：`node scripts/scope-check.mjs`，`verify` 的第一步，也是提交前必过项。
- 删除文件等同越界，必须显式申报。

## 5. 逐项完成（防偏移）

- **一次只做一件事**：只执行 `TASK.md` 描述的那个任务卡；做完 → 归档到 `{{TASKS_REL}}/` → 更新 `ROADMAP.md` → 再取下一个。
- 取任务只从 `ROADMAP.md` 任务队列的队首取，不得跳任务、不得并行开新任务卡。
- 上一个任务未 `done`（定义见 `CONSTITUTION.md` 第七条）之前，不得开始下一个。
- 上一个模块未 `done` 之前，不得开启有依赖关系的下一个模块。
- 计划变更（发现任务拆分不对）→ 更新 `ROADMAP.md` 并在 `TASK.md` 记录原因，不要默默改计划。
- 一张卡内可派并行子代理分片干活，但白名单仍单点定义、文件互不相交、**子代理自报不算证据**
  （`git status` / 全量验证 / 卡面数字由主控复跑复测）。
- 卡面是过程记录：漏复述就动代码、越界后补手续、探针临时插入又删除，都写进 `TASK.md`
  「流程偏差申报」（事实 / 影响 / 缓解 / 后续做法），不要事后淡化。

## 6. 硬禁止（不可协商）

1. **不得为通过测试而修改、删除、跳过测试**（含 `skip` / `only` / `xfail` / 放宽断言）。
   测试文件变更必须在 `TASK.md`「测试变更申报」说明理由，否则视为越界。
2. 禁止无理由的 `eslint-disable` / `@ts-ignore` / `# noqa` / `# type: ignore`；必须带任务 ID 与理由。
3. 禁止 `git reset --hard`、`git push --force`、`--no-verify`、跳过 hooks、改写他人提交。
4. 禁止修改：`{{MANIFEST}}` 的依赖声明、lockfile、CI 配置、数据库迁移、生产配置、
   `AGENTS.md` / `CONSTITUTION.md`（除非任务明确允许）。
5. 禁止读写凭据文件（`.env*`、`*.pem`、`credentials*`、密钥目录）；禁止把仓库内容外发到外部服务。
6. 禁止新增依赖。确需新增 → 走「范围变更请求」。
7. 禁止为了让检查通过而放宽 `scripts/consistency-audit.mjs` 的规则或往模板里塞假数据。

## 7. 编码规则（可读性）

**硬约束（由 lint 执行，以 lint 配置为唯一权威）**：嵌套深度、函数行数、圈复杂度、禁用 `goto` / 隐式跳转、
命名禁用空词、无未使用变量。配方见 `references/readability.md`。

**已判失败的规则在这里列清单**（写清参数与适用范围），形如：`unsafe_code`；嵌套深度；函数 >100 行；
参数 >7；复杂度过高；`dbg!` / `todo!`；**仅生产目标**：生产代码不得 unwrap（测试里 unwrap 是失败信号，
用带理由的作用域 allow 覆盖）。**晋升仪式**：新规则先用命令行量到 **0 违规**，再写进 lint 配置判失败；
本项目验证入口用 `--deny warnings`，所以清零之前**连 warn 都不能加**（挂上当天门禁就红）。

**建议（review 时检查，不作为卡点）**：早返回与卫语句优先；函数 30–80 行、文件 300–600 行为宜；
调用链 ≤ 3–4 层；避免单行转发；就近放置；重复三次再抽象；类型/副作用/错误/边界显式化；注释写 why。

**允许的小修（无需申报，但必须在报告中列出）**：本文件内的 typo、import 排序、行尾空格、因本次改动产生的失效注释。
除此之外一律先申报。

## 7.5 共享工作区纪律

本仓库常与别的进程、别人的长跑任务共处一台机器：①**清理只按自己记录的 PID**（`kill "$PID"`），
**禁止 `pkill` / `killall` 这类按名字匹配的清理** —— 它顺手杀过别人跑了很久的验证进程；
②启动的进程要在 `trap` / `finally` 里按 PID 收尾，脚本端口用可被环境变量覆盖的临时段；
③临时工作树与临时目录用完自己删（`git worktree remove --force <路径>`），且**不要放在 `/tmp`**（多数机器上它是小容量 tmpfs，构建产物会把它写满，连带别人的进程一起失败）—— 放仓库同盘目录。

## 8. 验证

- 写完一个可运行单元就跑相关测试；每完成一步更新 `TASK.md` 并跑 `scripts/verify.* --fast`。
- 涉及行为变化时，先写会失败的测试、看到它失败、再写实现让它通过（红绿证据写进 `TASK.md`）。
- `--full` 在**每个任务收尾**和**每个模块收尾**都必须跑，且必须包含 `consistency-audit`。
- 失败必须修复，或标记 `blocked` 并说明原因。**不得跳过。**
- 证据落盘 `var/verify-<时间戳>.log`；对话只给结论与路径，不给「应该没问题」。
