# 为什么每条规则长这样

这份文件是护栏的"遗嘱"。后来的人（或 Agent）想删规则前先读它 —— 每条都对应一个真实发生过的失效方式。

## 核心结论

**只写在 Markdown 里的约束，对 LLM 是建议而不是约束。** 一套规则若没有任何一条能被脚本拦住，
它在长任务里必然退化：上下文被压缩时规则最先被挤出去，而违规没有任何成本。

因此本套规范的分工是：

| 类型 | 落地方式 | 例子 |
|---|---|---|
| 必须绝对执行 | 脚本门禁（失败 exit ≠ 0） | 范围锁、npm script 存在性、日志留证 |
| 需要机械一致 | lint 配置 | 嵌套深度、函数行数、命名黑名单 |
| 需要判断力 | 文档 + review 清单 | 就近放置、抽象时机、注释写 why |

不要把第三类写成"必须" —— 无法检查的硬规则会稀释真正硬的那几条。

## 三道门禁的存在理由

### 1. `scope-check.mjs` —— 范围锁

**它拦住的失效**：LLM 在"顺手"的名义下改动范围外文件（改配置、升级依赖、格式化无关文件、
调整旁边模块的接口），导致 diff 无法 review、回归无法定位。

原文写法是"只允许修改 TASK.md 里列出的文件"——纯文字、无校验、无机器可读格式，等于没有。
改造要点：白名单升级为哨兵块（`SCOPE:MODIFY/CREATE/DENY`），由脚本与 `git status` 做差集。

**已知局限**：`TASK.md` 必须可写（每步都要更新它），所以 Agent 理论上能靠改 `TASK.md` 给自己扩权。
缓解措施是脚本在检测到 `TASK.md` 被改动时打印提醒，由人类核对 diff。
**不要用"把 TASK.md 也锁死"来解决** —— 那会让整个流程无法运转。

**判定顺序是 DENY → CREATE/MODIFY**（命中 DENY 直接违规）。这条顺序不能反过来：
DENY 的语义是"这次绝对不许碰"，让它被 CREATE 翻案就等于没有 DENY。
代价是"DENY 写整目录 + 同目录下写 CREATE"会造出**死信**（写进去了却永远不放行），
所以脚本在两者前缀重叠时打印警告（判定不变，只提示），`rules-task.md` 也给了差→好写法对照。

### 2. `verify.*` 的双模式与前置检查

**它拦住的失效**：

- 命令写错或不存在时，"验证通过"其实是假通过（原文硬编码 `npm run fmt:check`，却没检查脚本是否存在）。
- 从子目录执行导致路径错误 → 所以脚本强制 `cd` 到仓库根。
- 长任务里"验证结果"只有一句"通过"，无法追溯 → 所以日志落盘到 `var/`，`TASK.md` 只记路径。
- 每步都跑全量测试浪费严重、只跑全量又太慢 → 所以分 `--fast` / `--full`。
- 在 Windows 上 `bash` 不可靠 → 所以同时提供 `.ps1`。

### 3. "禁止改测试"

**它拦住的失效**：LLM 让测试变绿的最短路径不是修实现，而是改断言、加 `skip`、删用例、放宽类型。
一旦发生，整套验证闭环的价值归零，而且**在看 diff 之前很难发现**。

这条无法完全自动化（合法的测试变更确实存在），所以采取"禁止 + 显式申报"：
`AGENTS.md` §5 禁止，`TASK.md` 留「测试变更申报」区，`pre-commit.md` 列为卡点。

## 其他设计取舍

- **复述块写进文件，而不是只打印在对话里**：对话会被压缩、会被截断，文件不会。
  同时它也是"Agent 确实读过规则"的证据。
- **落掉"任务明确就直接执行"这句逃生门**：原文允许 LLM 自行判断"任务是否明确"，
  这等于把门禁的判断权交给了被约束方。改为显式的 `approval: human | auto` 字段，默认 `human`。
- **禁止清单单点定义**：原文在 `AGENTS.md` 和 `TASK.md` 各写了一份禁止文件列表，两份必然漂移，
  而且冲突时以谁为准没定义。现在只在 `TASK.md` 的 `SCOPE:DENY` 里定义一次。
- **prompts 不复制规则内容**：`start/continue/finish` 只写动作顺序并引用 `AGENTS.md`。
  复制即漂移 —— 两处规则冲突时，Agent 会挑对自己有利的那份遵守。
- **recon 模式**：调研、复现、排查类任务在原文框架下无范围可锁，会被"禁止越界"卡死，
  或者被迫编一份假计划来通过门禁。给一条只读通道比强行套执行流程更安全。
- **文件体积上限**：规则文件本身失控时，"每轮必读"会挤掉真正需要的上下文，
  规则自我拆台。所以 `AGENTS.md` ≤150 行、`ARCHITECTURE.md` ≤200 行。
- **冷启动 / 热续分开**：每轮全量读 6 个文件成本高且收益递减；热续只读 `TASK.md` + 变更文件 + 模块 README。
- **门禁自身要被验证**：`scope-check.test.mjs` 用 7 个用例覆盖拦截行为，
  并且全量 verify 会跑它 —— 护栏失效比没有护栏更危险。

# 第二轮：可读性、不偏移、逐项完成、整体一致

第一轮解决的是"LLM 会不会乱改"。第二轮解决的是四个更长远的问题：
代码可读、任务不漂、沿计划逐项推进、全部模块写完还像同一个项目。

## 借鉴自哪里

| 来源 | 借了什么 | 落地成 |
|---|---|---|
| superpowers（Agent 软件工程方法论） | 先出规格再写码；计划要细到"没品味的初级工程师也能照做"；红绿 TDD；**两阶段评审（先规格、后质量）**；"证据高于声明"；修 bug 必须先复现 | 计划步骤必须含文件路径+验证命令+预期；`task-review.md`；红绿证据；`verification.md` |
| GitHub spec-kit | **constitution 一次性定义项目级不变量**；per-feature 的 specify → plan → tasks → implement → converge；一致性分析作为独立质量门 | `CONSTITUTION.md`；ROADMAP 的模块+任务双层；`consistency-audit.mjs` |
| 业界架构适应度函数（fitness function） | 用可执行检查守住"架构意图"，而不是写文档期望大家自觉 | `consistency-audit.mjs` 的各项检查 |
| 自己的实战教训 | 归一化"重复定义必然漂移" | 白名单只在 TASK.md、规则只在 AGENTS.md、计划只在 ROADMAP.md |

## 各新增机制的取舍

### `CONSTITUTION.md`（项目宪法）

**它拦住的失效**：每个任务都"局部合理"，合起来风格各异 —— 三个模块三种错误处理、五种命名风格。
宪法只定义**跨模块的、可判定的不变量**，具体怎么做留给个案。

**为什么独立成一个文件**：`AGENTS.md` 是"怎么干活"（流程、门禁、禁止项），宪法是"什么算对"
（可读性、一致性、依赖方向、DoD）。混在一起的结果是两边都写不清楚，而且宪法要人类签字、
流程可以 Agent 执行，权限不同。

### `ROADMAP.md`（唯一计划源）

**它拦住的失效**：计划散落在对话里、issue 里、脑子里。Agent 每个会话只能看到"当前任务"，
于是"接下来做什么"永远靠猜，或者干脆自己发明一个新任务（这是最典型的偏移）。

**关键设计**：模块注册表是机器可解析的（`MODULES` 哨兵块），并且**依赖关系写在这里** ——
有了它，`consistency-audit` 才能判断"你引用的这个模块到底该不该依赖"。
一张人名表格是做不到这件事的。

**为什么要有阶段与顺序**：先做被依赖的模块。跳过依赖直接做上层模块，写出来的上层代码必然
带一堆临时假设，等地基补好时它已经烂了。

### 任务卡与归档（`TASK.md` → `docs/tasks/`）

**它拦住的失效**：`TASK.md` 被下一个任务覆盖 → 上一个人的判断、踩过的坑、红绿证据全部消失；
新会话无法恢复上下文，只能重新摸索（这就是"连续性"失守的地方）。

**做法**：TASK.md 是**唯一活跃**的任务卡；完成后原样归档，只追加一段结果摘要。
`consistency-audit` 会检查"标了 done 的模块有没有归档卡"——防止"声称完成但无痕迹"。

### 两阶段评审

**它拦住的失效**：单阶段评审容易滑向"代码风格挑刺"，而真正的问题是"这活儿压根不是要的那个"。
所以顺序固定：**先对规格（做对了没有），再对质量（做得好不好）**。阶段一不过，阶段二没有意义。

### 红绿证据

**它拦住的失效**："改完了，测试通过" —— 但没人知道测试是不是为了让改动通过而写的。
要求先有"看到它失败"的记录，实际上是在要求**有一个能复现问题的东西**。
附带好处：让"改测试骗绿"这件事无处藏身。

### `consistency-audit.mjs`（各项检查，清单以脚本输出为准）

**它拦住的失效**：lint 只管单个文件，测试只管单个行为。**没有任何工具看"多模块合起来"的样子。**
于是项目越大越不像一个项目：文档骗人、依赖乱指、同一能力三处实现、TODO 无人认领、
`handle` 满天飞、模板占位符还留在代码里。

设计上的两个判断：

1. **error 与 warn 分开**。可确凿判定的（文档声明了代码里没有的接口、依赖未声明）判失败；
   需要人判断的（跨模块同名导出、深引内部文件）只警告。把模糊项做成硬门禁，会让人绕过整个工具。
2. **`--report` 模式**。项目初期一定不干净，如果第一天就红，人会选择关掉它。
   所以 `--fast` 用 report 模式（只看），`--full` 才判失败 —— 让它在项目成熟过程中逐步收紧。

### `docs/contracts/`（契约 + 术语表）

**它拦住的失效**：并行/串行开发的多个模块对"同一个东西"有三种理解。
契约要求**先写约定再实现**，并且契约变更必须在同一任务内同步所有使用方 ——
不允许"先改提供方，使用方下个任务再说"（那必然忘记）。

术语表的作用最朴素：**同义词是 bug**。发现两个名字指同一个东西，当场全局合并，
不要留"两个都能用"（那就是未来的不一致）。

### 为什么模块注册表、任务队列、契约索引都只有一个

这是第一轮就确立的原则：**两处定义必然漂移**。
所以 ROADMAP 负责"做什么"，TASK 负责"正在做哪个 + 能改哪些文件"，
`docs/tasks/README.md` 里明确写了"不要手工维护任务总索引表，grep 就行"。

# 第三轮：Rust 支持与"已有治理体系"的适配

起因是一个真实场景：把本套规范落地到一个 Rust workspace（9 个 crate），
而该仓库已经有自己的上位治理体系（上级目录 AGENTS.md、外部决议登记表、扁平 docs + 不新开文档）。
两个问题同时暴露。

## 一、三条检查在 Rust 上其实是"静默不跑"

不是"通过"，是"没跑" —— 比报错危险得多，因为输出显示 ✓。

1. **`dependency-direction` 只认带引号的模块路径**（`import x from '../y'`）。Rust 写的是
   `use example_core::…`，没有引号，于是这条检查对 Rust 仓库永远无事发生。
   处理：按扩展名分派，Rust 分支拿 crate 标识符比对注册表的依赖声明。两个必要细节：
   crate 名要读 `Cargo.toml`（`[lib] name` 可覆盖包名，包名里的 `-` 在代码里是 `_`），
   而且要扫全文、不只扫 `use` 行（`example_core::foo()` 这种全限定路径同样建立依赖）。
2. **`duplicate-implementations` 的正则不认 `fn`**，Rust 下永远返回空。
   处理：补 `fn`/`struct`/`enum`/`trait`，并跳过语言惯例名（`new`/`from`/`main`…）——
   否则每个 crate 的 `pub fn new` 都报一次，**警告一旦变成噪音就等于没有**。
3. **`public-entry`（深引检查）对 Rust 跳过**，这是设计决定不是妥协：
   Rust 的 `pub` / `pub(crate)` / `pub(super)` 就是这条边界的执行者，rustc 已经在管，
   再扫文本只会对每个合法的 `use example_core::engine::Engine` 刷警告。
   关键是不能悄悄跳过 —— 脚本会打印 `public-entry(rust)` 一行，说明这里没查、以及为什么不查。

## 二、`docSection` 对"聚合模块文档"必须限定作用域

仓库纪律常常是"不新开文档"，一个模块一份 md 不被允许，多份模块只能共用一份文档。
此时 `docSection` 在全文档里找「职责」永远只命中第一个模块的块 ——
检查对每个模块都显示 ✓，实际一个都没查（又一种静默失效）。

处理：注册表的 `doc` 列可以全部指向同一份聚合文档，文档里每个模块用
`## <模块ID> <名字>` 起一个块；审计先按模块 ID 收窄作用域，再在块内找小节。
单模块文档（没有 ID 标题）退回全文，行为不变。

## 三、路径与入口不能钉死

- 计划源、归档目录、证据目录都做成参数（`--roadmap` / `--tasks` / `--evidence`）。
  理由：仓库可能已有自己的计划文档和目录命名（中文目录名很常见），
  钉死路径会逼人为了工具改名，或者干脆不用工具。
- `init_repo.mjs` 加 `--minimal`（只铺门禁，不铺规则文档）与 `--verify=none`（不铺 `verify.sh`）。
  理由：技能自己写着"不要新增第二条验证路径"，脚手架却无条件铺 `verify.sh` ——
  **规则与实现自相矛盾时，人一定照着省事的那条做**。仓库已有 `scripts/check.sh` 时，
  正确做法是把门禁接进去，而不是并排放一个 `verify.sh`。

## 四、判定尺度按语言分级：方法名不是自由函数名

`frame.data()` / `actor.handle(ev)` 由接收者补上了名词，属于 trait 与消息协议规定的动词
（同 `Iterator::next`、`Future::poll`）；`fn handle(ev)` 才是真的没写名字。
两者同等判失败，会逼着人给方法起别扭的名字，或者关掉检查。
处理：Rust 方法（签名含 `self`）降为警告，**且每次审计都打印**，让人看得见、可以自行决定要不要改名；
自由函数与类型名仍判失败。

## 五、既有 lint 阈值：先测量，再决定

给一个已有上万行代码的仓库加 `[workspace.lints.clippy]` 判失败，第一天必然全红，
而人应对全红的方式通常是关掉检查。所以顺序固定：先用命令行量违规数，
为 0 的规则才进 `Cargo.toml` 判失败，有违规的开任务卡进队列。
另外 `cargo clippy -- --deny warnings` 会把新加的 `warn` 级规则也变成失败 ——
"先测量"不是谨慎，是前置条件。

## 六、门禁自身的两个静默失效（落地当天被真实仓库逼出来的）

落地在一个**中文文件名**的仓库上时，两个一直在那里、但从没被发现的 bug 当场暴露：

1. **`scope-check` 把非 ASCII 路径变成乱码**。`git status --porcelain` 默认对非 ASCII 路径
   加引号并做八进制转义（`"docs/\344\275\277\347\224\250\346\211\213\345\206\214.md"`），
   原实现只 `replace(/^"|"$/g,'')` 剥外层引号，不还原转义 → 白名单永远匹配不上，
   **中文命名的文件全部被报成越界**。修法：改用 `git status --porcelain -z`
   （NUL 分隔、不转义、不引号），并顺手把重命名/复制的原路径也计入
   （`-z` 下原路径是紧随其后的一个 token，老代码靠 ` -> ` 分割，在 `-z` 下不存在）。
   自测补了两个用例：白名单内的中文路径要通过；越界时错误信息必须是可读路径而非 `\3xx` 乱码。

2. **`duplicate-implementations` 在 Rust 上全是假阳性**。实测一个 9 crate 仓库报出 33 条，
   逐条查看**全部**是方法：trait 声明在一个模块、实现在另一个模块，同名是设计要求
   （`StatusSource::status_json`、`FrameFramer::feed`）。另有 `-> Self` 构造器同名。
   这类噪音的最终结局一定是被无视，所以按语言再排两类：签名含 `self` 的方法、
   以及 `-> Self` 构造器（名字由返回类型限定）。排完 33 → 3，剩下 3 条是人该看的
   （PyO3 绑定层镜像了内核类型）。**收敛噪音不是放宽规则：留下 33 条真警告等于 0 条。**

两条的共性还是那句话：**静默失效比报错危险**。第 1 条如果不落地在一个中文仓库上，
可能永远不会被发现；第 2 条如果只跑空仓库的测试，也永远看不出来 ——
所以「护栏必须先在真实仓库上跑一遍」本身就该是流程的一部分。

## 已知局限（别假装它完美）

1. **`scope-check` 管不住"改规则文件"**：`TASK.md` 必须可写，Agent 理论上能靠改白名单扩权。
   缓解：脚本在 TASK.md 被改动时打印提醒，人类必须核对这份 diff。
2. **`consistency-audit` 是启发式的**：符号同步、跨模块引用靠文本扫描，会有漏报与个例误报
   （比如动态 import、字符串拼接路径）。它的定位是"抓住漂移的趋势"，不是"编译器"。
3. **文档新鲜度只比日期**：比的是"代码提交日期 vs 文档核验日期"，不能证明内容真的对得上。
   真正的一致性还是靠评审时对一遍。
4. **并发开发仍是薄弱点**：`TASK.md`、`ROADMAP.md` 是单写入者文件。多人/多 Agent 并行时
   必须按模块拆任务卡或走分支隔离，否则冲突会放大成范围失控。
5. **门禁挡不住"放弃"**：所有检查都可以通过删掉检查本身来通过。所以
   `AGENTS.md` §6.7 明确禁止放宽审计规则或塞假数据，并且这条只能靠评审兜底。
6. **Rust 文件的 `#[cfg(test)]` 之后不检查**：Rust 惯例把单元测试放在文件尾部，
   测试夹具会合法地包含反例（`fn handle`、坏 TODO），不豁免就会把工具逼到被关掉。
   代价是这些内联测试里的空词命名不会被发现 —— 与"测试文件跳过内容检查"是同一个取舍。
7. **接管既有仓库时，`scope-check` 第一天的保护是打折的**：门禁比较的是 `git status`，
   工作区里原有的在制改动会被算成越界。只能如实登记进基线任务卡的白名单，
   并在「未决问题」写清"这几份文件现有的保护暂时失效，收口后要移出白名单"。
   不写清楚就等于留了一个永久后门。

## 实现时踩过的坑（别重复踩）

写这套工具本身暴露了三个真实问题，都已在代码里修掉，记录在这里免得被"优化"回去：

1. **审计会把测试夹具当违规**。`naming` 与 `todo-task-id` 检查扫到测试文件里故意写的反例
   （`function handle()`、`// TODO 补边界处理`），导致新仓库第一天就报一堆错。
   处理：`.test.` / `.spec.` / `tests/` / `test_*.py` 与两个门禁脚本自身跳过内容检查（占位符检查保留）。
   代价是测试代码里的空词命名不会被发现 —— 这个取舍是划算的，因为假阳性能让人直接关掉工具。

2. **Markdown 分节用正则 `$` 会出错**。带 `m` 标志时 `$` 匹配每一行行尾，
   让 `([\s\S]*?)(?=\n#{2,3}\s|$)` 提前收尾，静默返回空节 → 检查失效但不报错。
   处理：改用按行扫描的 `docSection()`。**静默失效比报错危险**，这类检查要有测试盯着。

3. **模板渲染会误伤非模板文件**。`init_repo.mjs` 最初对所有文件做占位符替换，
   结果把测试文件里作为字面量出现的占位符也替换了，测试随之失效。
   处理：只对 `RENDER_ALLOWLIST` 里的文件替换，并在替换后扫描残留占位符给出提示。

第 3 条尤其值得记住：**通用替换 + 无白名单 = 迟早改坏不该改的东西**。

4. **同一个正则 `$` 的坑又踩了一次**。第三轮读 `Cargo.toml` 的 section 时写了
   `^\[lib\]\s*$([\s\S]*?)(?=^\[|\s*$)`：`m` 标志下 `$` 每行行尾都成立，非贪婪体当场匹配空串，
   section 永远读不到内容，crate 名全变 `null`，新写的 Rust 依赖检查**静默失效**。
   处理：改成按行扫描（与第 2 条同样的解法）。
   教训：凡是用正则切分"块状文本"（markdown 分节、ini/toml section、代码块），
   先按行扫描，别用 `$`。**同一个错误会以不同外衣回来**，所以每条检查都要有测试盯着 ——
   这个 bug 是被新加的 Rust 用例抓出来的，不是靠读代码看出来的。
