# 计划与一致性：怎么做到"逐项完成、整体不散"

这份文件回答两个问题：

1. 怎么让 Agent **沿着规划一项一项做**，而不是跳到最容易的地方？
2. 全部模块写完之后，怎么保证拼起来还是**同一个项目**？

---

## 一、逐项完成的机制：四个"只有一个"

偏移（drift）几乎都来自"同时存在多个真相"。本套规范的做法是让每个维度都只有一个源头：

| 维度 | 唯一源头 | 谁写 | 检查方式 |
|---|---|---|---|
| 做什么、什么顺序 | `ROADMAP.md` 的模块注册表 + 任务队列 | 人类定，Agent 更新状态 | `consistency-audit` 解析注册表 |
| 现在在做哪一个 | `TASK.md`（唯一活跃任务卡） | Agent | 一次只有一张，团队约定 |
| 可以改哪些文件 | `TASK.md` 的 `SCOPE:` 哨兵块 | 人类 | `scope-check.mjs` 强制 |
| 怎么算做完 | `CONSTITUTION.md` 第七条 DoD | 人类 | 评审清单 + `verify --full` |

### 一个任务的完整生命周期

```
ROADMAP 队列队首
   ↓ 取任务，复制模板生成 TASK.md（填 AC / SCOPE / 计划）
   ↓ 复述 + 等确认（approval: human）
   ↓ 拆计划：每步含精确文件路径、验证命令、预期结果
   ↓ 红 → 绿 → 重构（每步更新进度日志，跑 verify --fast）
   ↓ 两阶段评审（先规格、再质量）
   ↓ verify --full（scope-check + consistency-audit + 全量测试）
   ↓ 归档 docs/tasks/ + 更新 ROADMAP 状态
下一个任务（或模块收尾）
```

### 反偏移的三条硬规则

1. **不许跳任务**。队列顺序包含依赖关系，跳过去等于在没打好的地基上盖楼。
2. **不许并行开新任务卡**。想做的事写进 `ROADMAP` 队列，不写就说明它不重要。
3. **计划外的一切都写进「未决问题」**，不顺手做。这条看似低效，实际是把"上下文污染"成本挡在门外。

### 计划要细到什么程度

判断标准（借自 superpowers 的说法）：**计划要细到一个热情但没品味的初级工程师、
不了解项目上下文、且厌恶测试的人，也能照着做对。**

具体到每步都要有：精确文件路径 + 验证命令 + 预期结果。反例："优化订单查询"。

## 二、整体一致性的机制：三个层次

### 第 1 层：写代码前的一致 —— 宪法 + 契约 + 术语表

- `CONSTITUTION.md`：项目不变量（可读性、一致性、依赖方向、证据、不偏移、契约、DoD）。
  每条都可判定，Agent 每轮都要说明哪几条对本任务生效。
- `docs/contracts/`：跨模块接口、数据模型、错误码、事件。**先写契约再写实现**。
- `docs/contracts/glossary.md`：一个概念一个名字。同义词是 bug，发现就当场合并。

这一层解决的是"两个人/两个模块各写一套"的问题。

### 第 2 层：写代码时的一致 —— 模仿 + 就近 + 三次原则

- 新模块先找最像的既有模块抄结构（目录、命名、错误处理、测试组织）。
- 同目录内风格不可区分；跨目录时以 `docs/contracts/` 的套路为准。
- 不引入并行实现：已有能力必须复用。

### 第 3 层：写完之后的一致 —— 架构适应度函数

`scripts/consistency-audit.mjs` 是这一层的执行者。它检查的是 **lint 检查不到的东西**：
多个模块合在一起是否还像同一个项目。

它查什么：

| 检查项 | 拦住的问题 |
|---|---|
| `module-registry` | ROADMAP 注册表格式错、依赖指向不存在的模块 |
| `modules-exist` | 注册表里写了模块，代码里没有（done/doing 时是错误） |
| `module-docs` | 模块没有文档，或文档缺「职责/入口/依赖/对外接口」小节 |
| `doc-freshness` | 代码改了但文档的「最后核验日期」没更新 → 文档已经骗人了 |
| `doc-symbol-sync` | 文档声明的接口 `foo()` 在代码里找不到（或反过来漏写） |
| `dependency-direction` | 引用了未在注册表声明依赖的模块 → 依赖关系失控（JS/TS/Python 看路径，Rust 看 crate 名） |
| `public-entry`（警告） | 跨模块深引内部文件，绕过公开入口（Rust 由 `pub(crate)` 隐私系统执行，跳过并打印说明） |
| `naming` | 出现 `handle` / `data` / `util` 这类空词命名（Rust 方法降为警告，见下） |
| `naming(rust 方法惯用)`（警告） | 名字由接收者补足了上下文的方法名，仍逐条打印，只是不判失败 |
| `todo-task-id` | 未登记的 TODO（没人会认领的债） |
| `placeholders` | 模板占位符残留（`{{...}}`）→ 说明某处从没被真正填过 |
| `tag-docs-todo`（警告） | 规则文档里还留着 `TODO:` 待填内容 |
| `done-has-archive` | 模块标了 done，却没有任何归档任务卡 → 声称完成但无痕迹 |
| `verify-evidence` | 有模块 done 但没有任何验证日志 → 完成没有证据 |
| `duplicate-implementations`（警告） | 同一能力在多个模块各写一遍 |

清单以脚本输出为准（`--json` 可机器读）；**别在文档里复述条数**，两处定义必然漂移。

### 目录与文件路径可配置（单一来源：`.guardrails.json`）

不同仓库的计划源与目录命名不同。**唯一声明源是仓库根的 `.guardrails.json`**：

```json
{
  "roadmap": "docs/计划/唯一计划源.md",
  "tasks": "docs/任务归档",
  "evidence": "logs",
  "taskFile": "TASK.md",
  "docSections": ["职责", "入口", "依赖", "对外接口"]
}
```

铺脚手架时用参数写入这份配置：

```bash
node scripts/init_repo.mjs <仓库> --stack=rust \
  --taskdir=docs/任务归档 --roadmap=docs/计划/唯一计划源.md --evidence=logs
```

`consistency-audit` / `scope-check` / `verify.*` / `doctor` 都读它；CLI 参数只作临时覆盖。
输出里的 `配置=config … 计划源=… 归档=… 证据=…` 就是实际生效值 —— 结论可疑时先核对这一行。
英文仓库可把 `docSections` 改成本地语言小节名，不必改审计脚本。

**不要在 verify 入口或别处再抄一份路径。** 两处定义必然漂移；目录名改了只改 JSON 一处。

### 仓库禁止"一个模块一份文档"时：聚合模块文档

写侧纪律常常是"不新开文档"。此时不要让每个模块都指向同一份文档了事 ——
`docSection` 会永远只命中第一个模块的块，检查对每个模块都显示 ✓ 而实际一个都没查。

正确做法是让聚合文档带上模块 ID：

```markdown
## M2 example-core

> 最后核验日期：2026-09-16

### 职责
### 入口
### 依赖
### 对外接口
```

注册表 `doc` 列全部写这份文档的路径，审计会先按模块 ID（`## M2 …`）收窄作用域再找小节，
模块之间不会串味。**单模块一份文档的老写法不受影响**（没有 ID 标题就退回全文）。

### 空词命名的判定尺度按语言分级

同一份空词名单，在不同语言里严重程度不一样：

- JS/Python 自由函数、Rust 的 `fn`/`struct`/`trait`/`mod`：名字是唯一上下文 → **判失败**。
- Rust 方法（签名里有 `self`）：`frame.data()` / `actor.handle(ev)` 由接收者补上了名词，
  是 trait 与消息协议规定的动词（同 `Iterator::next`、`Future::poll`）→ **只警告，且每次打印**。

不放成静默通过，是因为"可以接受"和"看不见"是两回事：打出来才能让人自己判断要不要改名。
反过来，把方法名也判失败会逼着人起别扭的名字或者关掉检查 —— 那比少查几条更糟。

用法：

```bash
# 路径参数与 verify.* 顶部保持一致（归档目录改过名的仓库尤其重要）
AUDIT="node scripts/consistency-audit.mjs --roadmap ROADMAP.md --tasks docs/tasks --evidence var"
$AUDIT              # 判失败，任务/模块收尾用
$AUDIT --report     # 只报告（项目初期 / 巡检）
$AUDIT --json       # 给 CI 或看板
```

已接入 `verify`：`--fast` 时用 `--report`（只看不动手），`--full` 时判失败。
输出第一行的 `计划源=… 归档=… 证据=…` 是实际生效的路径 —— 结论可疑时先核对这一行。

## 三、全部模块做完之后

`ROADMAP.md` 底部有一份「里程碑验收」清单，最后一步必须逐项执行。它检查的是
**跨模块的端到端正确性**，这是单个模块测试永远覆盖不到的地方：

- 全局全量验证通过
- 一致性审计 0 error
- 端到端主流程真的跑通一次（不是"各模块单独测试都过了"）
- 契约与实现一一对应；每个契约都有真实的实现与使用方
- 文档核验日期全部更新（没有骗人的过期文档）
- 术语一致（抽查若干概念，代码/文档/文案用同一个名字）
- 无 `blocked` 任务、无未决阻断项

**这一步不做，就等于把"整体一致性"交给运气。**

## 四、何时该改计划

计划不是圣旨，但改计划必须有痕迹：

| 情况 | 做法 |
|---|---|
| 任务拆得太粗/太细 | 改 `ROADMAP` 队列，在 `TASK.md` 写原因 |
| 发现依赖关系搞错了 | 改注册表的 `依赖` 列，说明为什么之前判断错了 |
| 范围需要扩大 | 走「范围变更请求」，人类确认后再动白名单 |
| 发现之前某个模块的实现是错的 | 新开一个任务卡修，不要在**当前**任务里顺手改 |
| 规则本身不合适 | 写「宪法修正案 / 规则变更请求」，由人类决定 |

改计划的成本应该低到愿意改，痕迹又必须清楚到能被追问。
