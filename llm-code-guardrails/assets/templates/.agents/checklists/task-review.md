# 任务评审（两阶段）

顺序不能颠倒：**先看做得对不对，再看做得好不好**。
阶段一没过就评价代码风格，等于给错误的东西打磨表面。

评审对象是这张任务卡的 diff，不是整个仓库。评审人可以是人类，也可以是另一个 Agent —— 但必须重读一遍实际 diff，
不允许只信作者自己的总结（"作者说改了 X"不算证据）。

---

## 阶段一：规格符合性（做对了没有）

- [ ] 逐条对照 `TASK.md` 的验收标准：每条都跑了对应命令？输出贴在红绿证据里？
- [ ] 有没有做了「非目标」里明确排除的事？
- [ ] 有没有改动 `SCOPE:` 白名单之外的文件？（`scope-check` 是否通过）
- [ ] 有没有"顺手"改动：重构、升级依赖、格式化无关文件、修计划外的 bug？
- [ ] 计划里的每一步都有对应产出？偏差是否写明了原因？
- [ ] 契约影响一节是否诚实？改了接口的，使用方是否已在同一任务内同步？
- [ ] 新增的分支是否有测试覆盖，含至少一条边界或失败路径？
- [ ] 测试文件是否被动过？动过的话理由是否成立（而不是为了让测试变绿）？

**阶段一结论**：符合 / 不符合（列出缺口，任务保持 `in_progress`）

---

## 阶段二：代码质量（做得好不好）

可读性（对照 `CONSTITUTION.md` 第一条）

- [ ] 控制流线性、早返回；嵌套是否超过 3 层？
- [ ] 命名是否表达意图？有没有 `data` / `info` / `handle` / `process` 这类空词？
- [ ] 有没有单行转发的包装层、只有一个实现的接口、只用一次的工具函数？
- [ ] 相关代码是否就近放置？有没有为一个函数单独开文件？
- [ ] 注释是否只解释 why？有没有复述代码的废话注释？
- [ ] 新人读这段，10 分钟内能说出它在做什么吗？

一致性（对照 `CONSTITUTION.md` 第二条）

- [ ] 错误处理、日志、配置读取、数据访问的写法是否与既有模块一致？
- [ ] 命名是否与术语表一致？有没有引入同义词？
- [ ] 有没有重复实现既有能力？
- [ ] 目录与文件组织是否跟最像的那个老模块一致？

正确性与健壮性

- [ ] 错误路径是否有明确处理？有没有吞掉异常 / 空 catch？
- [ ] 边界（空值、空集合、极值、并发、超时）是否有交代？
- [ ] 有没有留下调试代码、注释掉的代码、临时开关？

**阶段二结论**：通过 / 有阻断项（列出，任务保持 `in_progress`）

---

## 收尾

- 两阶段都通过 → 任务可标 `done`，执行归档（见 `{{TASKS_REL}}/README.md`）。
- 有阻断项未清零 → 不得标 `done`，不得开始下一个任务。
- 有非阻断的改进想法 → 写成 `ROADMAP.md` 里的新任务，不要塞进当前任务。
